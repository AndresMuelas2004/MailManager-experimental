# Repository Guide — Project-Specific (maintained by Claude)

This file contains details specific to MailManager. Update it when the project changes (new providers, new endpoints, architectural shifts). Do not modify any `CLAUDE.md` file.

Note: the `GET /mailboxes/{mailbox_id}/emails` listing endpoint reads only from the local database (Services → Database, no provider API calls). Search is exposed via `q` (router validates `min_length=2`, `max_length=200`); the service runs `parse_search_query(q)` (`services_helpers`, the successor to `parse_search_tokens` on the listing path — `parse_search_tokens` still exists and is used by `contacts_service` (recipient suggestions), but no longer by the listing path) which decomposes `q` into three buckets: free-text tokens, Gmail-style operator clauses, and an `in:` box override. Free text builds the same `unaccent(lower(...)) ILIKE unaccent(lower(...))` predicate over `subject`, `from_email`, `from_name` (AND between tokens, OR between columns) — literal substring only, no stemming, no typo tolerance, no relevance ranking. The MVP scope decision (chosen over `pg_trgm` / `tsvector`) and its accepted limitations live in `docs/features/lupa.md` — the code shows what is implemented, that file shows what was deliberately left out and why. Migration `0020_create_extension_unaccent` enables the PostgreSQL `unaccent` extension; a fresh database that skipped it surfaces as `function unaccent(text) does not exist` at query time.

Note: the lupa operators (`from:` `to:` `subject:` `has:attachment` `before:`/`after:` `is:read|unread|favorite` alias `is:starred`, `in:`) are **ad-hoc search, never saveable** virtual-mailbox filters — this is the critical trap when extending either side. They travel only through `q`, are parsed in the service, and reach the repository via the dedicated `operator_clauses` parameter, resolved against `_OPERATOR_CLAUSE_BUILDERS` (a registry that lives ONLY in the repository, with no schema counterpart). The "two whitelists in lockstep" rule above (`_EXTRA_FILTER_BUILDERS` ⇆ `VirtualMailboxFilterPayload` / `ALLOWED_FILTER_KEYS`) governs **saved** filters and does NOT apply here: adding any operator key to `VirtualMailboxFilterPayload` would silently widen the saved-filter surface and is wrong. `VirtualMailboxFilterPayload`'s `extra="forbid"` must keep rejecting (422) every key that is not one of the six saved filters. The two surfaces apply `in:` **asymmetrically**: the regular/unified/Favoritos listing lets `in:` **override** the effective box (it wins over the route box and over the Favoritos `ALL_MAIL` anchor, while `is_favorite` stays — so `in:sent` means "favourites in Sent"); the virtual listing **intersects** `in:` with the vmbox's own box scope and short-circuits to an empty `EmailPageOut` (no DB call) when the requested box is incompatible with the vmbox's pinned box or its exclusion list. Operator-vs-saved-filter contradictions (`is:read` over a saved `is_read=False`, inverted date range) resolve to zero rows in SQL, not via code — see `database_guide.md`. `before:`/`after:` parse in `Europe/Madrid` (real CET/CEST, not a fixed offset), which needs the IANA tz database at runtime: `tzdata` is pinned in `backend/requirements.txt` (the container's only manifest — base image `python:3.12-slim-bookworm` does not guarantee the OS tz package) and is also required by any host venv (Windows `zoneinfo` has no system source) running the date-parser tests, hence the loose `tzdata` entry in the root `requirements.txt` too. The accepted behaviours and the full operator/value/date catalog live in `docs/features/lupa.md` + `docs/limits/lupa.md`.

Note: `email_metadata.to_email` / `to_name` (migration 0031) intentionally store **only the first** `To` recipient of the original message, not the full list. The inbox table has a single "Para" column and the dominant reading semantics — "to whom this went" — are well served by the primary destination; promoting to `TEXT[]` is a non-destructive future migration. Multi-recipient messages still keep CC / BCC at the provider (we never sync those into metadata), so showing only the head of `toRecipients` is a visualisation simplification, not a data-loss invariant. The `EmailTable` columns ("Para" / "De") are driven by the `(view, isSent)` matrix encoded in `resolveColumnLayout`: individual mailboxes show only the "other side" because the user's own account email is constant across rows (the listing is already scoped to one account), while unified mailboxes need both columns to disambiguate which of the user's accounts is involved. A regression that drops the `view`/`isSent` props on a new page would silently re-introduce the duplicated/redundant column the migration was meant to remove — pages that mount `EmailTable` MUST decide both props explicitly. The `view='mixed'` mode is the only mode that **ignores** the table-level `isSent` prop and resolves cell sense per-row from `email.box === 'SENT'`; it exists for listings that mix received+sent rows (Favoritos today). Mounting such a listing with `view='unified'` and a hardcoded `isSent={false}` silently degrades the "De"/"Cuenta" cells for every sent row (both columns collapse to the user's own account email) — the trap the `mixed` mode was added to close.
Note: the `GET /mailboxes/{mailbox_id}/emails/{id}/content` endpoint uses a cache-aside pattern — first verifies the email exists in `email_metadata` (404 `email_not_found` otherwise), then checks the `email_content` table, and on cache miss fetches from the provider API, runs the HTML through the dedicated rendering pipeline (`api.services.email_html_pipeline.prepare_email_html`, re-exported from `services_helpers` as `sanitize_email_html`), persists in DB, then returns. The pipeline is composed of seven pure functions in order: (1) `_normalize_charset_meta` strips any bogus `<meta charset="us-ascii">` / `<meta http-equiv="Content-Type" content="…charset=windows-1252">` and, **only when the input has a `<head>`**, injects a canonical `<meta charset="utf-8">` right after it so downstream parsers (lxml in premailer, html5lib in bleach) treat the Python `str` as UTF-8 instead of honouring a wrong declared charset (which would otherwise produce mojibake on accented characters); when there is no `<head>` the canonical meta is **not** injected — a Python `str` is already Unicode-decoded and prepending `<meta>` before any `<!DOCTYPE>` would push lxml into quirks mode; (2) `_unwrap_mso_conditionals` keeps the payload of downlevel-revealed comments (`<!--[if !mso]><!-- -->…<!--<![endif]-->` and the compact `<!--[if !mso]><!-->…<!--<![endif]-->` short form) and **discards** downlevel-hidden blocks entirely (`<!--[if mso | IE]>…<![endif]-->`, `<!--[if gte mso 9]><xml>…</xml><![endif]-->`, etc.) — those are Outlook-only layouts that must stay invisible in our iframe viewer (a non-Outlook client), and unwrapping them caused visible duplication whenever templates shipped both an MSO-only and a non-MSO variant of the same hero/logo (Medusa Festival #20, Santander Open Academy #73); when discarding hidden blocks leaves an empty body (>200 bytes discarded **and** <50 visible chars left), `_unwrap_mso_conditionals` logs `logger.warning("MSO-only email detected: discarded N bytes …")` so legacy MSO-only newsletters become observable instead of disappearing silently — no automatic fallback is applied; (3) `_sanitize_style_blocks` parses every `<style>` block with cssutils, filters properties against `_ALLOWED_CSS_PROPERTIES`, drops unsafe property values (`expression(…)`, `javascript:`, `vbscript:`), keeps only the at-rules in `_ALLOWED_CSS_AT_RULES` (`@media`, `@supports`, `@font-face`) and discards the rest (`@import`, `@keyframes`, `@namespace`, `@charset`) — each rule is wrapped in its own `try/except` so a single unparseable sibling rule (`calc(100% - )`, vendor-specific syntax, etc.) cannot wipe the whole block and take down preheader-hiding rules like `.preheader{display:none}` with it (bugs #5, #22, #51, #73, #84, #143, #315); the at-rule decision uses a `{rule_type: at_rule_name}` map consulted against `_ALLOWED_CSS_AT_RULES` (single source of truth — change the constant, not the function); this is also what lets responsive newsletter templates (eDreams, Netcapital, HubSpot-style) render their desktop layout inside the iframe because the `@media (min-width:…)` override now survives; (4) `_inline_css_via_premailer` runs premailer with `keep_style_tags=True` so inlinable rules go onto element `style=""` attributes for compatibility *and* the sanitised `<style>` tag survives for media queries / pseudo-classes; (5a) `_flatten_document_wrappers` strips head-only constructs that must not leak into the body fragment — `<!DOCTYPE>`, `<title>…</title>` (otherwise bleach would keep the inner text and render the subject as visible body content — Pencil.dev #36), `<meta>`, `<link>`, `<base>`, stray `<xml>` islands (MSO leftovers), plus the `<html>`/`<head>`/`<body>` wrapper tags themselves — and **preserves the outer `<body>`'s `style`/`bgcolor`** by promoting them into a synthetic wrapping `<div style="…">` so the iframe's own `body{background:#fff}` reset does not cover HubSpot/Netcapital's lavender frame (bugs #8, #9); the wrapper's style attribute is escaped with `html.escape(quote=True)` so a `<body>` style mixing single and double quotes (e.g. `font-family:"Helvetica Neue",'Arial'`) cannot break the wrapper attribute (CSSSanitizer cleans the CSS later); (5b) `_mirror_geometry_to_attributes` mirrors `width`/`height` values from inline styles back onto HTML attributes on `<img>`/`<td>`/`<th>`/`<table>` so signature tables and inline logos keep their intended dimensions even if the inline style is later stripped — the defensive guard counts `img`/`td`/`th`/`table` elements (via `_CRITICAL_ELEMENT_RE`) before and after the lxml reparse, abandoning the step when the post-reparse count drops below half the input (lxml's cosmetic byte deltas — entity escaping, attribute requoting — no longer trigger false positives the way the previous 50 %-byte guard did); (6) `_strip_script_blocks` removes `<script>` blocks with their content (but *not* `<style>` anymore — its content was sanitised in step 3); (7) `_clean_with_bleach` applies the final tag/attribute/protocol allowlist with `"style"` in `_ALLOWED_TAGS` and `CSSSanitizer(allowed_css_properties=_ALLOWED_CSS_PROPERTIES, allowed_svg_properties=frozenset())` filtering inline `style=""` attributes. Allowed protocols: `http`, `https`, `mailto`, `cid`, `data`. The legacy `background` HTML attribute is allow-listed on `table`/`td`/`th` — EDM templates (AliExpress product grids) paint thumbnails via `<td background="https://…">` instead of `<img>`, so removing it from `_ALLOWED_ATTRIBUTES` silently degrades those cells to **grey placeholders** (bleach keeps the cell's `background-color` but drops the image URL); bleach protocol-checks it exactly like `src`. `cid:` backgrounds ride the same attribute (`inline_cid_images` rewrites `cid:`→`data:` in place on `background="…"`), so they were stripped too until the attribute was allow-listed. During the provider fetch, inline images referenced as `<img src="cid:…">`, `background="cid:…"`, or `style="background-image:url(cid:…)"` (the latter produced by premailer when it inlines `<style>` rules) are resolved to `data:image/<type>;base64,…` URLs by traversing Gmail's `multipart/related` tree (with an extra `attachments().get()` call when the part carries only an `attachmentId`) or by requesting Outlook's `GET /me/messages/{id}/attachments?$select=contentType,contentBytes,contentId,isInline` when `hasAttachments` is true; both providers apply the shared helper `core.email.helpers.inline_cid_images` with per-image soft fallback. Gmail's body decoder (`_extract_body_from_payload`) delegates base64 + charset decoding to the shared helper `core.email.helpers.decode_mime_body`, which implements a UTF-8-first strategy with validated fallback: try strict UTF-8 first (any well-formed UTF-8 body decodes correctly), on `UnicodeDecodeError` fall back to the charset declared in the part's `Content-Type` header, and as last resort decode UTF-8 with `errors="replace"`. This prevents the mojibake that happened when senders mislabelled UTF-8 bodies as `iso-8859-1` or `windows-1252` — Outlook (Graph API) does charset negotiation server-side so it is unaffected. Content rows are tied to metadata via a composite foreign key `email_content.(provider_message_id, account_id) → email_metadata.(provider_message_id, account_id) ON DELETE CASCADE`, so metadata deletes and account deletes transitively cascade into content (migration 0013). Migration 0014 truncates `email_content` once to invalidate any HTML cached before the CSS-inlining + `cid:` pipeline was introduced; migration 0015 does the same after `data:` URLs were added to the sanitizer's allowed protocols; migration 0016 does the same after MSO unwrap + `url(cid:…)` resolution + Gmail charset detection; migration 0017 does the same after charset meta normalisation + geometry attribute restoration; migration 0018 does the same after the pipeline refactor (extraction into `email_html_pipeline.py`, `<style>` preservation with sanitised `@media`/`@supports`/`@font-face` rules, and Gmail's UTF-8-first body decode); migration 0019 does the same after head-only tag scrub + `<body>` background promotion + MSO-hidden discard + resilient per-rule `<style>` sanitisation + geometry reparse guard; migration 0035 does the same after allow-listing the legacy `background` attribute on `table`/`td`/`th` (table-cell background images stop being stripped to grey placeholders); migration 0036 does the same after the body+attachments provider read was unified into a single call (`fetch_content_with_attachments`) — and is also the migration that adds the sliding-TTL `last_accessed_at` column (see the cache-aside Note below for the TTL + prefetch behaviour).
Note: the `POST /mailboxes/{mailbox_id}/accounts/{account_id}/drafts` endpoint follows the Provider-First Rule — the draft is created at the provider first (Gmail `drafts.create` or Outlook `POST /me/messages` with `Prefer: IdType="ImmutableId"`), and only on success persisted to the local `drafts` table. The composer also invokes this endpoint **silently** the first time the user attaches a file in `new_email` / `new_draft` mode (the attachment endpoints below need a real `provider_draft_id` to bind to — D-07 lazy push only applies to the attachment bytes, not to the draft container itself); a single in-flight ref in `useDraftComposer` (`creatingDraftRef`) collapses concurrent drops into one call so two simultaneous drops never produce two drafts. Side effect to be aware of: an empty draft becomes visible in Gmail/Outlook web during composition of a "new email" before the user has explicitly saved — see `docs/features/adjuntos.md` § 6.8 variant.
Note: the `POST /mailboxes/{mailbox_id}/accounts/{account_id}/drafts/{provider_draft_id}/send` endpoint follows the Provider-First Rule — the draft is sent at the provider first (Gmail `drafts().send()` or Outlook `POST /me/messages/{id}/send` with `Prefer: IdType="ImmutableId"`), with 3 total attempts on transient failures. Only on success are DB changes applied: the `drafts` row is deleted (which CASCADE-removes `draft_attachments`) and the sent email metadata is persisted to `email_metadata` — both as best-effort (failures are logged but do not fail the response). Gmail returns a new `message_id` for the sent email; Outlook keeps the same ID thanks to ImmutableId. The send path now goes through `EmailManager.send_draft_with_attachments`: Gmail builds a fresh `multipart/mixed` MIME and replaces the draft contents in a single atomic `drafts.send` (or its `uploadType=resumable` variant when total MIME > 5 MB, picked by `pick_gmail_send_strategy`); Outlook is non-atomic — it uploads each pending attachment via `POST /me/messages/{id}/attachments` (<3 MB) or `createUploadSession` + chunked PUT (≥3 MB, picked by `pick_outlook_attachment_strategy`), persists each returned `provider_attachment_id` immediately, then fires `POST /messages/{id}/send`. On a mid-flight failure the partial successes are persisted **before** re-raising `EmailAttachmentSendFailed`, so a retry skips already-uploaded parts (D-27 partial-success resume). Behaviour-level documentation: `docs/features/adjuntos.md`. The frontend's `useDraftComposer.handleSendEmail` reroutes "Send" through this endpoint (instead of `POST /emails/send`) whenever a silent draft bootstrap has happened in `new_email` mode — `POST /emails/send` cannot carry locally-stored draft attachments, so a regression that drops the reroute would silently send an empty-bodied email and leave the attachments orphaned in `draft_attachments`.

Note: the interactive account-connect flow is **two-phase by necessity, not preference**: the backend runs headless inside a Podman container, so the old single-call `/connect` (which ran `InstalledAppFlow.run_local_server` / an embedded callback server and `webbrowser.open` in the API process) physically cannot work — there is no browser in the container and an ephemeral callback port is never published (`could not locate runnable browser` was the visible symptom). `POST .../connect` now only returns `{authorization_url, state}`; the SPA opens it in a popup (opened `about:blank` synchronously inside the click gesture — popup blockers kill a `window.open` issued after the awaits) and the provider redirects to the API's own published port: `GET /auth/google/callback` / `GET /auth/outlook/callback`, which complete the exchange, persist tokens, and report back to the opener via `postMessage` (fallback: on silent popup close the hook probes `GET /accounts/{id}` and treats a non-null `email_address` as proof of success). The pending flow between the two phases lives in `api/services/oauth_pending.py` — **in-memory, single-worker only** (Gmail's entry holds the live `Flow` object carrying the PKCE verifier; it cannot be serialized, and a `--reload` restart mid-flow voids the pending state by design). Redirect-URI asymmetry: Gmail's is `GOOGLE_OAUTH_REDIRECT_URI` (default `http://localhost:8000/auth/google/callback`; the Google client is a "Desktop app", which accepts any localhost redirect unregistered), Outlook's comes from the credentials JSON and must match the Azure app registration exactly (`http://localhost:8000/auth/outlook/callback` — already registered there). **Frontend rollback invariant**: the account row is created before the OAuth starts (the flow needs its `account_id`), so `useConnectedAccounts.addAccount` deletes the account and shows no card whenever the flow does not end in a confirmed connection — the card only ever appears for a connected account. **Reconnect asymmetry**: `useConnectedAccounts.reconnectAccount` re-runs the SAME `/connect` on an **already-existing** account_id (a previously-connected account whose token died) and — unlike `addAccount` — **never deletes the account on failure** (a regression that adds a rollback there would destroy the user's account + synced emails); it also cannot reuse `addAccount`'s silent-close `email_address` success-probe (the account already has an email), so it confirms the new token by re-syncing instead. The personal script `backend/Scripts/cli_utilities/connect_account.py` still imports the removed single-call service function and is stale (Scripts/ is out of Claude's scope).

Note: the favourites toggle `PATCH .../emails/{message_id}/favorite` follows the Provider-First Rule, but the local-existence pre-check (`email_metadata_store.exists`) runs **before** the provider call — a missing row must collapse to 404 `email_not_found` without spending a Gmail/Outlook round trip, mirroring the `DraftNotFound` pre-check pattern used by the drafts surface. A successful provider call followed by an `update_favorite` that affects zero rows surfaces as 404 too (race: the row was deleted between the pre-check and the update) — never silently succeeded. `is_favorite` is ORTHOGONAL to `box` / `is_read`: a favourite stays favourite as it moves between INBOX / SENT / SPAM / TRASH (matching how both providers model it — Gmail `STARRED` coexists with every other label, Outlook `flag` travels with the message). The toggle is idempotent at both providers; the partial index `(account_id, received_at DESC) WHERE is_favorite = TRUE` (migration 0027) backs the dedicated Favourites listing without bloating the index with the much-larger non-favourite majority.

Note: the `box` query param interacts asymmetrically with `favorite=true` on `GET /mailboxes/{mailbox_id}/emails`. `box=ALL_MAIL` is treated as the "anywhere except TRASH/SPAM" anchor (the dedicated FavoritesPage in the frontend always passes ALL_MAIL because TanStack Query needs SOME box param for query-key stability); every other value (`SENT`, `SPAM`, `TRASH`) is honoured literally. The previous implementation collapsed any non-{TRASH, SPAM} value into the anchor, silently leaking ALL_MAIL favourites into the SENT favourites view — the regression test `test_listing_with_favorite_and_explicit_sent_box_returns_only_sent_favorites` exists to prevent the regression coming back the next time someone refactors the favourite/box interaction.

Note: `POST /favorites/sync` deliberately mixes responsibilities asymmetrically: the provider gives us the source of truth (favourite ids per account), and the DB-side single-statement update `UPDATE email_metadata SET is_favorite = (provider_message_id = ANY(:true_ids)) WHERE account_id = :aid` marks every provider-favourite TRUE and **every other row of the account FALSE in the same transaction** (atomic from the caller's perspective). A favourite that exists at the provider but NOT in our local `email_metadata` is silently skipped — the sync explicitly does NOT import new metadata rows (Option A in `Ignore/Favoritos-Funcionalidad.md`). The general `/emails/sync-metadata` endpoint owns that responsibility; rebuilding it inside `/favorites/sync` would mix label-only and metadata-fetch quota costs and double-count rows. The response's `total_synced` is the rowcount across the account (every row touched), while `accounts[i].favorites_synced` is the cardinality of `list_favorite_ids` (the count of true ids returned by the provider). They are deliberately not equal.

Note: virtual mailboxes (`/virtual-mailboxes`, table `virtual_mailboxes`) carry a snapshot of `account_ids` (a flat list inside `scope_payload`). Eliminating one of the real mailboxes referenced by that list does NOT cascade — the FK is `users(user_id) ON DELETE CASCADE`, not `accounts(account_id)`. The listing path re-validates ownership at every read and silently drops accounts the user no longer owns, so the vmbox stays alive but shows only the surviving subset instead of 404'ing. Migration 0032 dropped the original `scope_kind` indirection (`all` / `mailbox` / `accounts`) and snapshotted pre-existing rows into explicit lists — newly connected accounts therefore do NOT auto-join legacy bandejas that were created with the old `scope='all'` mode. The "why" lives in `docs/features/bandejas-ficticias.md`. Opening a virtual mailbox **syncs its accounts first** (so a stale account behind the vmbox surfaces its newest mail before the listing renders), but that orchestration lives **entirely in the frontend**: it fans out one `POST /mailboxes/{mailbox_id}/emails/sync-metadata?account_id=...` per resolved account (the endpoint is per-mailbox + optional single account, never a list), reusing each row's real `mailbox_id` from the listing JOIN. The vmbox listing service itself stays **100% local-only and must never import `core`** — keeping the provider machinery on the frontend side is the deliberate reason the open-sync was not pushed into `virtual_mailboxes_service` (root `CLAUDE.md` §4 boundary); a regression that adds a `from core...` line there to "sync inside the listing" breaks that invariant. Second trap: `_build_filter_args` injects `DELETED` into **every** `box_not_in` branch (default, custom override, and the `box_not_in: []` opt-in), so a hard-deleted message is **never** visible in a vmbox even under "exclude nothing". `DELETED` is not a `FilterBox` member, so it cannot be requested; the positive `box = X` predicate excludes it for free, but the negative `box_not_in` predicate (`AND NOT (box = ANY(...))`) would leak it without this — the same "DELETED never shows in a negative view" discipline as `LIST_RECIPIENT_SUGGESTIONS`' `box NOT IN ('SPAM','TRASH','DELETED')`. It is a permanent non-saveable exclusion: do NOT add `DELETED` to `FilterBox` / `VirtualMailboxFilterPayload`.

Note: virtual mailbox listing shares its `WHERE`-clause builder with the regular box listing — both route `box` / `q` / `extra_filters` through the single repository helper `_build_filter_predicates`, which fills the three `str.format` slots (`{box_predicate}`, `{search_predicate}`, `{extra_predicate}`) of `LIST_FILTERED` (and its `*_DISTINCT` / `COUNT_*` variants) in `database/queries/email_metadata.py`. The regular `GET /emails` passes `box = ALL_MAIL|SENT|SPAM|TRASH` (mandatory); the virtual listing passes `box = None` plus an explicit `box_not_in` (or `box`) derived from `filter_payload`. The repository's `list_filtered` accepts all three forms — passing more than one at the same time is a programming error (the service layer guarantees exclusivity). The two surfaces diverge only on the SELECT template: the virtual listing passes `distinct_provider_message_id=True` so it runs `LIST_FILTERED_DISTINCT` (cross-account dedup done in SQL, BEFORE `LIMIT`/`OFFSET`), the regular listing runs plain `LIST_FILTERED`. Sharing the predicate builder avoids drift between near-identical SQL strings; **a future filter criterion must extend two whitelists in lockstep**: `_EXTRA_FILTER_BUILDERS` in the repository AND `VirtualMailboxFilterPayload` (which `ALLOWED_FILTER_KEYS` is derived from) in the schema. Adding only one of them produces either silent SQL injection surface or silent 422s on the API boundary. The lupa operators ride the SAME `{extra_predicate}` slot via a SEPARATE registry (`_OPERATOR_CLAUSE_BUILDERS`, repository-only) appended after the `extra_filters` clauses — no new slot — and the lockstep rule does NOT apply to them because they are not saveable filters (see the lupa-operators Note above and `database_guide.md`).

Note: both listing endpoints return a paginated envelope `EmailPageOut` (`items` + `total` + `limit` + `offset`), not a bare `EmailMetadataOut[]`. `total` is the exact count of the WHOLE filtered set in the local synced copy — never the provider's live mailbox size, never the page length — produced by `count_filtered`, which the service drives with the SAME predicates as `list_filtered` (the `tokens` AND the `operator_clauses` from a single `parse_search_query(q)` are computed once and passed identically to both calls, so the count counts exactly what the page lists). The two store calls sit in separate `try` blocks only so their failure messages stay globally unique (API `CLAUDE.md` §7); a count failure raises `EmailListError` / `VirtualMailboxListError` (500) with its own message. The vmbox total is a `COUNT(DISTINCT provider_message_id)` so it does not over-count the cross-account duplicate the listing collapses. The frontend derives numbered pages from `offset`/`limit`/`total` (`page = offset/limit + 1`, `total_pages = ceil(total/limit)`); "has more" is intentionally not a field. The router default `limit` dropped from 200 to 50, but the service-layer signature default stays 200 — direct service callers and tests that omit `limit` are unaffected; only the HTTP `Query(default=...)` changed.

Note: conversation grouping is a SECOND listing mode layered on the same machinery. `GET /emails` takes `group_by_thread` (default off); the virtual listing forces it ON always; **Favoritos stays ungrouped** (the frontend passes `group_by_thread=False`, and the backend respects the flag without a `favorite`-coupled override — `favorite=True`+`group_by_thread=True` is valid "group the favourites" SQL, just not a product surface). The grouping key is `COALESCE(NULLIF(thread_id,''), provider_message_id)` (a `''`/NULL `thread_id` becomes a singleton keyed by its own message id; threadless rows never merge). The four grouped templates (`LIST_/COUNT_GROUPED_BY_THREAD` and their `*_DISTINCT` variants) collapse a thread into its most-recent message, aggregate `is_read`=`bool_and`, `has_attachments`/`is_favorite`=`bool_or`, and project `thread_message_count` = messages of the thread **present in that box and already synced locally** (NOT the conversation's absolute size — decision 3). `total` counts threads. ⚠️ **Grouping-key asymmetry, identical in spirit to the `*_DISTINCT` dedup**: the regular listing partitions by `(account_id, thread_key)` (never fuses two distinct accounts of a unified mailbox, even on a pathological shared `thread_id` string); the virtual listing partitions by `thread_key` alone (after the inner `provider_message_id` dedup) so it collapses the same provider account connected under two mailboxes. The COUNT template MUST follow the same `distinct` axis as its LIST or the `total` descuadra — `_select_count_template` mirrors `_select_list_template` precisely for that reason. Detail in `database_guide.md`; the `q` (search) match is per-message so a thread surfaces if ANY of its messages matches even when the shown representative doesn't (`database/queries/email_metadata.py` § 2.6).

Note: the `GET .../accounts/{account_id}/emails/{provider_message_id}/conversation` endpoint (mounted on `favorites_router` like `reply-context`) is **read + lazy sync, NOT Provider-First** (it reads the thread from the provider and best-effort completes the local copy — same family as `get_email_full_content` filling `email_content`, so it is NOT in the Provider-First exception list). It is keyed by `provider_message_id` (path-safe) and derives the thread from the base row; a threadless base row short-circuits to a single-message `ConversationOut` with NO provider call. ⚠️ **Counter-vs-viewer source asymmetry** (the load-bearing trap): the LISTING thread row's `is_read`/`has_attachments`/`is_favorite`/`thread_message_count` come from the **DB** (window aggregates over the synced copy), but `ConversationOut.messages` is mapped from the **provider's fresh state on this open** (membership + per-message box/is_read/favourite), so a message moved/read out-of-band shows correctly in the viewer even if the best-effort lazy sync that follows failed. The viewer's per-message `has_attachments` is **always `False`** (B.lazy — the clip appears when the body is opened via the content endpoint and `recompute_has_attachments` runs); `is_favorite` IS faithful because `ConversationMessage` carries it (unlike `EmailMetadata`). "Completing the mailbox" persists older thread messages but, thanks to the per-thread grouping, does NOT split the active box's pages (they fold into the already-visible thread row, only its counter grows — decision 7); the frontend invalidates the listings afterwards to refresh counts/order.

Note: `EmailMetadataOut.mailbox_id` is the email's REAL mailbox, projected from a JOIN with `accounts` (the `email_metadata` table does NOT carry the column — accounts own the mailbox_id and a single email belongs to exactly one account). The frontend uses this field to route every per-email side action (open content, mark read, toggle favourite, move to trash, mark spam, download attachment) to the right `/mailboxes/{mailbox_id}/...` endpoint instead of the URL's mailbox_id. The drift only surfaces inside a virtual mailbox whose `account_ids` span multiple real mailboxes — the listing surfaces emails whose account lives in a DIFFERENT mailbox than the route, and using the route's mailbox_id then 404s with `account_not_found` because the backend validates `account ∈ mailbox` on every per-email path. Bulk operations (`useEmailBulkActions`) handle the same asymmetry by grouping selected emails by `mailbox_id` and fanning out one HTTP call per group; a regression that reverts to a single call with the route's mailbox_id would silently 404 every cross-mailbox selection inside a multi-mailbox virtual bandeja.

Note: `useVirtualMailboxEmails` overrides the global TanStack Query defaults with `refetchOnMount: 'always'` + `staleTime: 0`. The global default (`staleTime: 30_000` in `QueryProvider`) is the right caching policy for stable inbox listings, but virtual mailboxes are user-curated, time-sensitive views — the user expects newly arrived emails to surface the moment they re-open the view, not after 30 s. A regression that drops the override silently re-introduces the "stale for 30 s" behaviour the user explicitly asked to avoid.

Note: the recipient-autocomplete endpoint `GET /contacts/suggestions?q=…&limit=…` is **user-level** (no `/mailboxes/{id}` prefix — it aggregates across EVERY account the user owns, resolved by session via `account_store.list_account_ids_by_user`, calquing the `/virtual-mailboxes` ownership model). It is **local-only — no provider call** (no new OAuth scope), exactly like the lupa: the suggestions are built entirely from already-synced `email_metadata`. The single SQL `LIST_RECIPIENT_SUGGESTIONS` collects candidates from BOTH `from_*` (senders of received mail) and `to_*` (recipients of sent mail) restricted to `box NOT IN ('SPAM','TRASH','DELETED')`, dedupes by `lower(email)` (one entry per address regardless of casing / source account), keeps the most-recent non-empty display name, orders by frequency then recency, and **excludes the user's own connected-account addresses** (`accounts.email_address`). The net effect of the box filter + own-address exclusion is that received rows contribute the external sender and sent rows the external recipient (the symmetrical own-side column collapses out as a self-address). Tokens are shared with the lupa (`parse_search_tokens` → accent-/case-insensitive substring, AND between tokens, OR over the (email, name) pair). **No migration and no index** (MVP head stays 0032): the leading-wildcard `ILIKE '%…%'` cannot use a B-tree, same deliberate trade-off as the lupa (`pg_trgm` GIN was rejected there) — see `database_guide.md`. Two cross-surface traps: (1) the `to_email` partiality (migration 0031 stores only the FIRST `To` recipient) means "to whom you sent" coverage is limited to primary destinations — CC/BCC recipients of your sent mail are never suggested; (2) the backend excludes only OWN + SPAM/TRASH addresses — filtering out addresses **already typed into the active recipient field** is the frontend's job (`RecipientAutocompleteInput`), because the server never sees the in-progress line. The behaviour-level docs and exact caps live under `docs/features/` / `docs/limits/`.

Note: virtual mailbox validation is **two-phase**. (1) Pydantic at the schema boundary: `VirtualMailboxCreate` and `VirtualMailboxFilterPayload` both carry `extra="forbid"` — unknown top-level keys (e.g. `accountIds` camelCase) and unknown filter keys (e.g. legacy `from_domain`, now removed) collapse to 422 instead of being silently dropped into a "valid but empty" vmbox. The free-text filter fields (`from_email`, `subject_contains`) carry `min_length=1` to block `""` at the boundary — without it `subject_contains=""` would collapse to `ILIKE '%%'` inside the repository's `_filter_subject_contains`, matching every row and turning "filter by nothing" into a silent full-inbox dump indistinguishable from "no filter". The correct way to clear a filter is to omit the key, never to send `""`. (2) The service cross-checks every `account_id` against the user's owned account set on create AND update — unowned ids collapse to 404 `account_not_found` (not 403) to avoid leaking which accounts exist via UUID guessing (same D-22-style anti-leak policy as attachment ownership). Foreign virtual mailbox ids (read / update / delete / list-emails) collapse uniformly to 404 `virtual_mailbox_not_found`. **Race policy for UPDATE/DELETE on vmbox**: when the ownership pre-check passes but the row vanishes between pre-check and the mutating SQL, the repository returns `None` (update) or `False` (delete) and the service surfaces 404 `virtual_mailbox_not_found` — never a silent 200 on DELETE nor a generic 500 on UPDATE. A regression here (e.g. `store.update` raising `QueryError("not found")` and bubbling up as `VirtualMailboxOperationError`) would mask a real conflict between concurrent tabs.

Note: the composed email **body is HTML end to end** (rich-text composer). It is sanitised at the trust boundary — `create_draft` / `update_draft` / `send_email` run `api.services.outbound_html_pipeline.sanitize_outbound_html` (re-exported from `services_helpers`) over `payload.body` once and reuse the cleaned value for both the provider call and the persisted row; `send_draft` reads the already-clean row. This is a **different, stricter** sanitizer than the inbound viewer's `sanitize_email_html` (`email_html_pipeline`) — the two are NOT interchangeable, and a regression that points one at the other either lets composer markup through to the provider or strips a newsletter the viewer needs. On the wire: **Gmail** assembles a `multipart/alternative` (a `text/plain` leg derived from the HTML via `html_to_plain_text_alternative` FIRST, the `text/html` part SECOND; `multipart/mixed` wraps it when attachments are present); **Outlook** sends `body.contentType = "HTML"`. Asymmetry to know: only Gmail carries an explicit `text/plain` alternative — Outlook's JSON path gives Graph no way to control whether a text alternative is generated, so a recipient on an HTML-less client gets whatever Graph synthesises. `DraftOut.body` and `ReplyContextOut.body` are HTML (the reply/forward quote is an attribution line + `<blockquote>`; the user types above it). The body is capped at `max_length=1_000_000` on `DraftCreate` / `DraftUpdate` / `EmailSendRequest` — over the cap is a **422** emitted with FastAPI's default `{"detail": [...]}` envelope (no `RequestValidationError` handler is registered), distinct from the API's `{"error": {...}}` shape; a client surfacing "body too large" reads `detail[]`. There is **no `body_format` field** — every layer treats `body` as HTML unconditionally (migration 0034 + the provider-draft parsers backfill legacy plain-text drafts). The strict outbound allowlist and the inline `<blockquote>` quote style (`core.email.helpers._HTML_QUOTE_BLOCKQUOTE_STYLE`) must stay in lockstep — every CSS property the quote uses has to be in the sanitizer's allowlist or re-sanitising the seeded reply body would strip the quote frame.

Note: Reply / Reply All / Forward draft creation goes through the **same** `POST /drafts` endpoint as a blank draft, but the wire path diverges sharply per provider. Gmail builds a single `drafts.create` call with `message.threadId` plus RFC 5322 `In-Reply-To` and `References` MIME headers injected via the shared `build_mime_with_attachments(..., extra_headers=...)` plumbing — those three together are Gmail's **triple-requirement** for thread membership, validated locally **before** the round trip by `core.email.helpers.validate_reply_threading_coherence` (raises `EmailReplyContextFetchError` with `detail.reason ∈ {"thread_id_mismatch", "message_id_not_referenced", "subject_mismatch"}` so the user sees a deterministic error instead of an opaque Gmail 400). Outlook routes through `_create_draft_via_reply`, which posts to `/me/messages/{id}/createReply` / `createReplyAll` / `createForward` with the full message body in the **same** JSON call (R-09 single round trip — no follow-up PATCH). Outlook fixes `conversationId` server-side, so `thread_id` / `in_reply_to` / `references` are accepted on the contract for signature symmetry with Gmail but **discarded on the wire** (Graph offers no header-injection path on `createReply` nor `/send`). The wire shape is XOR-strict on the `createReply*` body: only `{"message": {...}}` is accepted — adding a sibling `comment` or root-level `toRecipients` produces a guaranteed 400, so the client pre-validates the recipients are nested under `message` and pre-rejects empty `toRecipients` for `reply` / `reply_all` (R-09). `forward` allows empty recipients (composer fills them later).

Note: Forward attachment inheritance is **asymmetric** between providers. Outlook's `createForward` copies the original message's attachments server-side as part of the creation call, so `drafts_service._persist_outlook_forward_inherited_attachments` calls `manager.list_message_attachments` immediately after draft creation and persists each downloadable row into `draft_attachments` with `blob=NULL` and `provider_attachment_id` already populated — the bytes live only in the provider draft and the Outlook send path will skip re-uploading them (D-27 contract: non-null `provider_attachment_id` means "already at the provider"). Gmail has **no** server-side copy primitive, so the frontend follows up with `POST /drafts/{pdid}/attachments/copy-from-email`, which downloads each source attachment binary (cache-aside via `email_attachment_store.get_blob` first, then provider fetch on miss) and re-inserts it into `draft_attachments` with the bytes carried inline. The endpoint is **uniform on the frontend** — `useDraftComposer.openForReplyKind` calls it unconditionally after every Forward draft creation — and **a no-op for Outlook** (returns `copied_count=0` with the current chip list so the composer reseeds without an extra round trip). The endpoint always responds **200 even on partial failure**: per-attachment failures (provider 404/410, size cap, count cap, already-copied) surface via the `skipped[]` array with structured `{filename, reason}` records instead of a 207/multi-status. Idempotency is R-12: `draft_attachment_store.list_existing_source_attachment_ids` reads the `source_attachment_id` column (migration 0030) and any candidate already present is reported as `reason="already_copied"` — a retry after a network blip is safe and does not duplicate rows.

Note: the reply / forward metadata stored on each `drafts` row (migration 0029) is the **single source of truth** at send time. The frontend reads the six reply columns from `DraftOut` and propagates them into `useComposerForm` state (`seedFromDraft` populates `replyMetadata` even though no UI renders them today — without that propagation a future "convert draft to forward" feature would silently lose threading), but `buildDraftPayload` deliberately omits them from the PATCH/POST body. The backend's `send_draft` reads them from the local row and passes them to `EmailManager.send_draft_with_attachments`. A regression that adds the six fields to the frontend send payload would let a tampered client overwrite the threading at send time; a regression that removes the row reads on the backend would silently break threading on every reply send. **Companion silent trap**: `UPSERT_DRAFTS_BATCH` wraps every one of the six reply columns in `COALESCE(EXCLUDED.col, drafts.col)` because `sync_drafts` pulls drafts back from the provider **without** any reply metadata (Gmail / Outlook do not expose these as draft properties on the read path) — a plain `EXCLUDED.col` assignment would clobber the locally-persisted reply fields on every drafts sync. The direction is the right one only because the sync path always passes NULLs for these columns; if a future caller starts populating them, the COALESCE must be revisited.

Note: Outlook's `createForward` carries a subject-editing trap that the frontend deliberately does NOT warn about: if the user edits the `Subject` field of the resulting Forward draft beyond the `Fwd:` prefix, Graph reassigns the message a new `conversationId` when the draft is saved, so the sent message detaches visually from the original thread in Outlook web. Accepted MVP behaviour — Gmail does not exhibit this because forwards are not enforced to share `threadId` (a Forward is allowed to start a new thread). The same asymmetry shows up in Gmail's API gap on the other side: the "Forwarded" indicator visible in Gmail web's UI is **UI-only** and not exposed by the REST API (no `FORWARDED` label, no field on `messages.get`), so any future "this email was forwarded" badge in our inbox would need a heuristic on the original `References` chain rather than a provider read. Outlook does not expose a reliable equivalent via Graph either.

Note: Outlook OAuth scope requirements split between draft creation and send. `createReply` / `createReplyAll` / `createForward` require `Mail.ReadWrite`; `POST /me/messages/{id}/send` requires `Mail.Send`. The Reply / Forward flow needs **both** in the same access token. Drop either from the app registration and the failure manifests at different points (draft creation 403 vs send 403) — useful when diagnosing scope downgrades on existing tenants. The `Prefer: IdType="ImmutableId"` header that every Outlook draft-mutation call must repeat extends to `createReply` / `createReplyAll` / `createForward` as well (Graph does not remember the preference across calls — see `core_guide.md`).

Note: `get_reply_context` runs the Gmail triple-requirement guard (`validate_reply_threading_coherence`) **only for `reply` and `reply_all`** — `forward` is excluded from the subject check because the `Fwd:` prefix legitimately diverges and Gmail does not require subject parity for forwards. A regression that runs the guard unconditionally would 502 every Forward against a real Gmail thread.

Note: `_persist_outlook_forward_inherited_attachments` is **best-effort, soft-fail**. A discovery failure or per-row insert failure is logged and swallowed — the composer still opens and the user can refresh to see the chips appear via `list_drafts` (which reads from `draft_attachments` directly). The post-insert `batch_update_provider_attachment_ids` pass matches each freshly-inserted row to its Graph-returned `provider_attachment_id` by **filename**, not by id (Graph returns the attachments in a separate listing call that does not preserve insertion order). A duplicate filename inside the same Forward would map both rows to the same `provider_attachment_id`; the matching is "first non-inline match wins" so the duplicate's row stays `provider_attachment_id=NULL` and the send path treats it as "still pending upload". Accepted MVP — duplicate filenames inside one forwarded message are vanishingly rare and the worst case is a redundant re-upload of bytes Graph already has.

Note: drafts attachments are the **only** mutating draft endpoints that intentionally do NOT follow the Provider-First Rule. `POST /mailboxes/{mailbox_id}/accounts/{account_id}/drafts/{provider_draft_id}/attachments` and `DELETE .../attachments/{draft_attachment_id}` write **only** to the local `draft_attachments` table — the provider draft is not touched until the user clicks Save/Send (D-07 lazy push). The rationale lives in `docs/features/adjuntos.md` § 6.9: Gmail's `drafts.update` rebuilds the entire MIME on every call, so eager uploads cost O(n²) bandwidth for n attachments; Outlook hits the 4-concurrent-requests-per-mailbox cap and accumulates 429s. The accepted side effect is that Gmail/Outlook web cannot see the in-progress attachments until Save/Send (documented edge case 6.8). The attachment endpoints share `Depends(enforce_multipart_size_limit)`, which rejects `Content-Length > 30 MB` with 413 `request_too_large` before reading the body — the 5 MB cushion above the 25 MB per-file cap (D-01) covers multipart boundary overhead.

Note: the `GET /mailboxes/{mailbox_id}/accounts/{account_id}/emails/{provider_message_id}/attachments/{attachment_id}` endpoint is a cache-aside binary stream (D-06). The service verifies ownership via a single SQL JOIN over `email_attachments → email_metadata → accounts → mailboxes` (no leaking foreign attachments via UUID guessing — D-22, missing rows surface as 404 `attachment_not_found`, NOT 403). On `unavailable_at IS NOT NULL` it short-circuits to 404 `attachment_unavailable` without touching the provider — that flag was stamped by a previous fetch returning 404/410 (D-17). On cache miss it authenticates the provider client, downloads the binary (provider 404/410 stamps `unavailable_at` then raises `AttachmentUnavailable`; 403 → `AttachmentProviderForbidden` 502; persistent 5xx → `AttachmentProviderUnavailable` 503), persists into `email_attachment_blobs`, and streams the bytes back. The router wraps the iterator in a `StreamingResponse` with `Content-Disposition` built by `core.email.helpers.format_content_disposition` (RFC 5987 + ASCII fallback in a single header), `X-Content-Type-Options: nosniff`, and `Cache-Control: private, no-cache`. A `BackgroundTask` refreshes `last_accessed_at` after the stream completes so the TTL purge only acts on truly idle blobs. **CORS trap (load-bearing for the filename):** `Content-Disposition` is NOT on the CORS response safelist, and the frontend is cross-origin (:5173 → :8000, no Vite proxy), so the browser can only read the real filename when `create_app()` mounts `CORSMiddleware` with `expose_headers=["Content-Disposition", …]`. Drop it and every download silently falls back to a name-less `attachment-<uuid>`. **Defence in depth:** the frontend also threads the metadata `filename` into `downloadEmailAttachment` as the fallback used when the header is unreadable — both sides together close the bug; either alone fixes it for the current environment, but the pair is the agreed scope. `nosniff` means the browser will not correct a wrong `Content-Type`, which is why the persisted `mime_type` must be right at discovery time (see Attachments Storage Layout).

Note: the `GET /mailboxes/{mailbox_id}/emails/{id}/content` endpoint also discovers and persists the message's downloadable attachments on cache miss (D-13 strict rule). The cache-miss path now makes a **single** unified provider read — `manager.fetch_content_with_attachments` returns the body, the downloadable list AND the inline `cid_map` together (D4 — one round trip instead of the old two: `fetch_email_content` + `list_message_attachments`) — then upserts the rows into `email_attachments`, and recomputes the `email_metadata.has_attachments` flag via the centralised helper `services_helpers.recompute_has_attachments`. The strategy chosen for `has_attachments` is "B.lazy puro": the flag stays `False` after sync and becomes `True` on the first `get_email_content` call that discovers downloadable parts — sync paths (`fetch_email_metadata`) deliberately do NOT touch `email_attachments`, even though Gmail's `format=METADATA` and Outlook's delta query both expose a `hasAttachments` boolean. The `EmailContentOut.attachments` field is read on **every** call (cache hit too), so a TTL purge that wipes `email_attachment_blobs` keeps the metadata consistent (`is_downloaded` flips to `false` and the next click triggers a re-download). Migration 0024 truncates `email_content` once after the strict inline-vs-attachment split (D-13) so HTML cached under the legacy "every inline part embedded as data: URL" rule is forced to refresh.

Note: `email_content` is no longer a forever cache — it carries a **30-day sliding TTL** (column `last_accessed_at`, migration 0036), the SAME interval and intent as the attachment-blob TTL, so it is pure space eviction (the body is immutable; the TTL never invalidates freshness). The model has three moving parts and several silent traps. (1) **Touch on hit.** The cache-hit branch of `get_email_full_content` calls `touch_email_content_last_accessed` (best-effort, soft-fail) which bumps **only** `last_accessed_at` via `TOUCH_LAST_ACCESSED` — **never** `fetched_at`. This asymmetry is load-bearing: the E2E cache-hit assertions (`test_46b`/`46d`) pin `fetched_at` unchanged across a read, and `GET_BY_MESSAGE_ID` never projects `last_accessed_at`, so a regression that touched `fetched_at` here would go red. On cache miss no separate touch is needed — `UPSERT_EMAIL_CONTENT` already stamps `last_accessed_at = now()` (alongside `fetched_at = now()`), so a fresh entry starts its TTL on persist. (2) **Purge.** Each `POST .../sync-metadata` (both the bootstrap and the delta path) evicts, off the response, the synced accounts' bodies idle 30+ days via `PURGE_EXPIRED_FOR_ACCOUNTS` (a single `DELETE … WHERE account_id = ANY(...) AND last_accessed_at < now() - INTERVAL '30 days'`). It is **per-account** and there is **no scheduler and no admin purge endpoint** (deliberately unlike the attachment-blob purge `POST /admin/attachments/purge`): a body of an account that is never synced again is never purged — an accepted MVP limitation. (3) **Prefetch.** After persisting metadata, the same background task pre-caches, **sequentially and message-by-message** (D2 — the sequential walk sidesteps both providers' per-user / per-mailbox concurrency 429s; the manager is reused already-authenticated from the sync, no re-auth and no token re-persist in the seconds the prefetch runs), the body of up to **50** of each account's **unread**, **≤48h**, **`ALL_MAIL`** messages whose body is **not yet cached** (`LIST_UNREAD_RECENT_UNCACHED`; the cap is `_PREFETCH_LIMIT` in `emails_service`, the 48h window and the `ALL_MAIL` box live in the SQL). Order is **purge first, then prefetch** (free space, then refill). The whole task is best-effort: every failure (selection, per-message fetch, purge) is logged and swallowed so it can neither affect the already-sent sync response nor abort the remaining messages. **Critical trap — the prefetch persists body AND attachments**, not just the body: it reuses the shared `_fetch_and_persist_email_content` helper (the same one the cache-miss viewer uses). Persisting only the body would make the first open a cache **hit** that never re-discovers attachments (discovery happens only on the unified read), hiding the clip and the attachments forever on pre-cached mail. **Router/contract trap:** the prefetch+purge is scheduled only when the router injects FastAPI `BackgroundTasks`; `sync_email_metadata` takes `background_tasks` keyword-only with default `None`, so direct service callers and the ~20 unit tests that omit it skip the optimisation entirely and the `SyncResultOut` contract is unchanged. Behaviour-level docs + exact figures: `docs/features/visualizacion-de-correos.md` + `docs/limits/visualizacion-de-correos.md`.

Note: the body+attachments unified read (`fetch_content_with_attachments`, core) **retired only `fetch_email_content`** — `list_message_attachments` SURVIVES because it has a second live call site, `drafts_service._persist_outlook_forward_inherited_attachments` (Outlook `createForward` attachment inheritance, D-27). The two coexist by consumer, not by accident (a dead-code reviewer flagging the duplication is wrong): the unified method fuses body+attachments for the viewer/prefetch; `list_message_attachments` lists only the attachments of a draft for the Forward path. The unified method classifies attachments **unconditionally** whenever the read succeeds (a text-only body can still carry downloadables; an inline-only HTML body reports Outlook `hasAttachments=false` yet still needs its `cid:` images resolved — D-13) — unlike the old `fetch_email_content`, which guarded classification behind `if html_body` (Gmail) / `hasAttachments` (Outlook). Detail in `core_guide.md`.

Note: the `POST /admin/attachments/purge` endpoint (D-30) is the **manual** TTL purge — there is no scheduler in MVP. It deletes `email_attachment_blobs` rows where `email_attachments.last_accessed_at < now() - INTERVAL '30 days'` and returns `{purged_count, freed_bytes}`. Auth is intentionally minimal: a single env var `ATTACHMENTS_PURGE_TOKEN` matched against the `X-Admin-Token` header. **Three states**, each surfacing its own code/status: env var unset → 503 `purge_disabled` (deploy not configured — distinguishes "we don't run this here" from "your token is wrong"); env var set but header missing/wrong → 401 `invalid_admin_token`; otherwise execute. Only the blob is purged; `email_attachments` keeps the row so a subsequent click triggers re-download on cache miss.

Note: the strict inline-vs-attachment rule (D-13) is enforced inside both provider clients (`gmail_client._classify_attachments`, `outlook_client._classify_attachments`). A part is treated as inline (embedded as `data:` URL in the HTML) **only** if all four conditions hold: `Content-Disposition: inline` (or Outlook `isInline=true`), the `Content-ID` is referenced by the rendered HTML body via `cid:…` (matched by the shared helper `core.email.helpers.find_referenced_cids`, which inspects both `src=`/`background=` attributes and CSS `url(cid:…)` after premailer inlining), the part has bytes, and the MIME type starts with `image/`. Otherwise the part is promoted to a downloadable attachment row in `email_attachments`. This avoids two failure modes from sloppy senders: inline-marked-but-unreferenced parts disappearing silently, and a `Content-ID`-bearing PDF being hidden inside the HTML. Migration 0024 invalidates HTML cached before this rule.

## Attachments Storage Layout

- **`email_attachments`** — one row per downloadable part of a received email. Composite FK `(account_id, provider_message_id) → email_metadata` with `ON DELETE CASCADE` AND `ON UPDATE CASCADE` (the latter is load-bearing: Outlook rewrites `provider_message_id` on `move_to_trash` / spam moves, and the cascade propagates the rename into the attachment rows automatically — without `ON UPDATE CASCADE` every move would orphan the attachment metadata).
  - **`filename` / `mime_type` are resolved at discovery, never freehand.** Because the download response carries `X-Content-Type-Options: nosniff`, the browser cannot correct a wrong type — so the right `mime_type` must be persisted up front. `mime_type` goes through `core.email.resolve_attachment_mime_type` (priority: specific declared type, case preserved > `mimetypes.guess_type(filename)` for generic/absent declared types > `application/octet-stream`); this unified both providers and removed Outlook's old `contentType.lower()`. `filename` is sanitised with `sanitize_filename` (per-email dedup) inside `_persist_attachment_metadata`, matching the draft path. Gmail additionally recovers an empty `MessagePart.filename` from `Content-Disposition: filename=` / `Content-Type: name=` headers (Outlook has no equivalent — see `core_guide.md`). **No migration accompanies these (Option A):** the CORS+frontend fix resolves the download-name bug for all attachments without one; the hardening (sanitisation / MIME inference / Gmail header recovery) applies only to attachments discovered or re-discovered after the fix (any email whose `email_content` cache is absent/invalidated re-runs `_classify_attachments`).
- **Two partial unique indexes** encode the provider key asymmetry. Gmail rows key by `(account_id, provider_message_id, part_id) WHERE part_id IS NOT NULL`. Outlook rows key by `(account_id, provider_message_id, provider_attachment_id) WHERE provider_attachment_id IS NOT NULL AND part_id IS NULL`. The split is intentional — a single null-tolerant compound index left Outlook rows colliding silently because `part_id` is always `NULL` for Outlook. The repository's `upsert_batch` partitions input rows by which key they carry and runs one `execute_values` per partition, each targeting its own index by name in the `ON CONFLICT` clause — passing a mixed batch is supported but each row only resolves against its own index.
- **Provider key asymmetry, why both columns exist.** Gmail's `attachmentId` is **not declared stable** in the docs — observed to change between calls — so we never persist it; we cache by `part_id` (immutable per the docs) and rediscover the `attachmentId` via `users().messages().get(format=FULL)` whenever a download is needed. Outlook's `id` IS stable while the message stays in the same mailbox **provided every call sends `Prefer: IdType="ImmutableId"`** (Graph does not remember the preference per-message — drop the header on any follow-up and the same ID is reinterpreted as a transient ID returning 404).
- **`email_attachment_blobs`** — separate one-to-one table holding the binary in `BYTEA`. The split keeps `SELECT *` over metadata cheap and lets the TTL purge remove the bytes without dropping the metadata row (the derived `is_downloaded` flag in `LIST_EMAIL_ATTACHMENTS_BY_MESSAGE` flips back to `false` and the next click re-fetches). The columns `blob_storage_kind` (`'db'` | `'fs'` | `'s3'`) and `blob_ref` are reserved for a future migration to filesystem / object-store backends; today every blob is `'db'` with `blob_ref = NULL`.
- **`draft_attachments`** — single table storing both the metadata AND the binary inline (no separate `_blobs` table). Composite FK `(account_id, provider_draft_id) → drafts(account_id, provider_draft_id) ON DELETE CASCADE` so deleting / sending the draft also removes its attachments. Drafts are short-lived and bounded by 25 attachments per draft (D-03), so the two-table split applied to received attachments would be over-engineering here. `provider_attachment_id` is `NULL` until the Outlook send path uploads the attachment; Gmail's atomic send path leaves it permanently `NULL`. **Forward-copy source tracking (migration 0030, R-12).** `source_account_id` + `source_attachment_id` are populated **only** by `copy_attachments_from_email` (direct uploads leave both NULL). The partial index `idx_draft_attachments_source ... WHERE source_attachment_id IS NOT NULL` keys the idempotency check `list_existing_source_attachment_ids` so a retried copy after a network blip skips the already-landed rows instead of duplicating them. The Outlook inheritance path (`createForward` server-side copy) leaves both columns NULL — Outlook-inherited rows are not retryable via this endpoint because the bytes live only at the provider and the row is already complete after creation; carrying source tracking for them would invite spurious "already_copied" hits on a Gmail-side retry of a mixed-provider chain.
- **`email_metadata.has_attachments`** — denormalised boolean (migration 0023) so the listing endpoint can render the clip icon without an extra JOIN per row. It is written **only** by `services_helpers.recompute_has_attachments` (which derives it from `COUNT(*) WHERE is_inline=false` against `email_attachments`) — never freehand. The B.lazy strategy means a row stays `false` until the user opens the email even when the provider already knows the message has attachments; this is intentional and documented in `docs/features/adjuntos.md` (sections 5 and 10).
- **`drafts.body` — renamed in migration 0022, re-HTML'd in migration 0034.** The column was originally `body_html` (historical HTML editor), renamed to `body` in migration 0022 when the composer was briefly a plain `<textarea>`, and now holds **HTML** again (the rich-text composer). Migration 0034 is a one-shot data conversion of every pre-existing plain-text `body` to its HTML equivalent (HTML-escape `&`/`<`/`>` then `nl2br`, wrapped in `<p>`); idempotent (skips blank or already-HTML rows) and mirrored as identical SQL in `database/migrations/runner.py`. There is **no `body_format` discriminator** — from 0034 on, `body` is unconditionally HTML. The 0022 rename ripple stands (queries, repository, schemas Pydantic + Zod, provider clients, draft API parameters); the field is `body`, not `body_html`. Companion read-path coverage lives in core: `_parse_gmail_draft` / `_parse_outlook_draft` convert any legacy plain-text draft that re-enters via `sync_drafts` back to HTML, so the migration and the parsers together keep every local row HTML (see `core_guide.md`).

## Playwright MCP output directory — silent trap

The `@playwright/mcp` server's `checkFile` guardrail permits writes to any path inside the process `cwd` AND inside `outputDir`, not only the latter. Claude Code spawns the MCP with `cwd = <repo>`, so an explicit `filename` passed to `browser_take_screenshot` / `browser_pdf_save` is resolved against the **workspace** via `workspaceFile()` and **bypasses** the `outputDir` returned by `outputFile()`. `--output-dir` alone is therefore not enough: a bare `filename="x.png"` lands in the repo root and the guardrail lets it through. Three independent layers cover this together — CLI flag in `.mcp.json` (`playwright` server), PreToolUse rewrite in `.claude/hooks/normalize-playwright-filename.py`, PostToolUse sweep in `.claude/hooks/sweep-playwright-artifacts.py` — and **dropping any one of them re-opens the leak silently**. The sweep specifically exists because `mcp__playwright__browser_evaluate` and `mcp__playwright__browser_run_code_unsafe` execute arbitrary Playwright code (e.g. `page.screenshot({ path: '...' })`) that does not flow through the MCP's `outputFile` / `workspaceFile` plumbing, so neither the rewrite hook nor the MCP's own guardrail can intercept them.

## Key Identifiers

- `mailbox_id` — groups accounts under a mailbox.
- `account_id` — unique per account record.
- `account_label` — `"{mailbox_id}__{account_id}"`, used by `EmailManager` for client identification.
- `display_label` — required on account creation (`min_length=1`, `NOT NULL`); the service layer falls back to `"{provider}:{account_id}"` when rendering responses for legacy records.
- `user_id` — UUID identifying an authenticated user (from `users` table).
- `owner_user_id` — FK on `mailboxes` linking to the owning user (NOT NULL, CASCADE on user delete).
- `email_address` — the email address of the connected account, fetched best-effort from the provider during `connect_account`. Stored as plain text (not encrypted) in the `accounts` table. May be `NULL` if the fetch failed.
- `provider_draft_id` — the draft identifier returned by the provider (Gmail `drafts.create` or Outlook `POST /me/messages` with `Prefer: IdType="ImmutableId"`). Together with `account_id`, forms the composite PK of the `drafts` table.
- `attachment_id` — local UUID PK of `email_attachments`. Generated by the service when a message's attachments are listed for the first time; **never** the provider's identifier — see "Provider key asymmetry" above.
- `provider_attachment_id` — Outlook `attachment.id` returned by Graph (`POST /messages/{id}/attachments` body or extracted from the `Location` header of `createUploadSession` — last URL segment of the form `Attachments('<id>')`). Stable while the message stays in the same mailbox **only when every Graph call sends `Prefer: IdType="ImmutableId"`**. For draft attachments this column doubles as the partial-success marker: `NULL` means "not yet at the provider", non-null means "already uploaded — skip on retry" (D-27).
- `part_id` — Gmail MIME part identifier (`payload.parts[].partId`). Used as the Gmail-side cache key in `email_attachments` because Gmail's `attachmentId` is not declared stable.
- `draft_attachment_id` — local UUID PK of `draft_attachments`. The composer references it on remove and the partial-success persist path uses it as the join key against the upload result list.

## Host Python Environment

The host interpreter for this project is the venv at repo-root **`.venv`** (`.venv\Scripts\python.exe` on Windows) — never the global Python and never any other venv. The silent trap: the agent's PowerShell/Bash tool spawns a fresh shell that does **not** inherit an activated venv, so a bare `python` / `pip` resolves to the **global** interpreter and installs or runs in the wrong place (e.g. `pip install tzdata` landing in the global site-packages while `.venv` stays missing it). Always invoke the project interpreter explicitly: `.\.venv\Scripts\python.exe -m pip ...`, `.\.venv\Scripts\python.exe -m pytest ...`. Recreating the venv must install from `backend/requirements.txt` (where host-only deps like `tzdata` live — Windows `zoneinfo` has no system tz source, so a venv missing it crashes test collection at `ZoneInfo("Europe/Madrid")` in `services_helpers.py`).

## Testing

- **E2E tests** (`backend/tests/e2e/`) — automated like unit and integration tests. They test all endpoints except interactive OAuth flows (`POST /auth/google`, `POST .../connect`) and `DELETE /auth/me` (cannot create a test user without the interactive login). Real third-party APIs and real DB persistence. Pre-configured test accounts are already inserted in the database with valid tokens and must never be deleted — E2E tests can be run without additional setup.

## Provider-First Rule

For any operation that modifies email state both at the provider and in our database, always call the provider API first. Only update the DB for messages where the provider call succeeded. Never persist a state change locally if the provider rejected or failed the operation. This ensures our DB always reflects the real state of the user's mailbox at the provider.
**Current exceptions:**
- Both providers (Gmail and Outlook) use a uniform no-op approach for `delete_messages` — the provider API is not called and deletion is performed only in the local database. See `core_guide.md` (Trash Management Operations > `delete_messages`) for the detailed rationale.
- Draft attachments lazy push (D-07): `POST /drafts/{id}/attachments` and `DELETE .../attachments/{aid}` write only to `draft_attachments`. The provider draft is updated transactionally during `send_draft` (atomic for Gmail; non-atomic + D-27 partial-resume for Outlook). Rationale in `docs/features/adjuntos.md` § 6.9.

## Containerisation (Podman) — load-bearing rules not visible in `compose.yml` alone

- **`backend` mounts `./frontend:/frontend:ro`** even though the backend never reads frontend code at runtime. The bind is load-bearing for `tests/integration/test_blocked_extensions_parity.py`, which computes its target path as `Path(__file__).resolve().parents[3] / "frontend" / "src" / "lib" / "blocked_extensions.json"` — inside the container that resolves to `/frontend/...`, so dropping the bind silently turns those 4 tests into `Failed: Frontend mirror not found`. The bind is read-only so a misbehaving backend cannot mutate frontend source.
- **`WATCHFILES_FORCE_POLLING=true` (backend env) and `vite.config.ts server.watch.usePolling: true` (frontend code)** are both load-bearing under WSL2 / Podman bind mounts. Without them inotify never fires across the Windows↔Linux bridge and `--reload` / HMR go silent — code edits land but no reload happens, no error logged. Verified empirically: removing either makes the smoke-test edit-and-reload loop fall back to "manual restart".
- **`frontend/Dockerfile` needs both `--legacy-peer-deps` AND `--ignore-scripts` on `npm install`.** Two unrelated reasons collide here: (a) `@testing-library/react@16.0.1` declares peer `@types/react@^18` while the project ships `@types/react@^19.2.5` → npm 10 strict-resolves and fails with `ERESOLVE` unless you ask for legacy peer behaviour; (b) `package.json`'s `prepare` script wires husky via `git config core.hooksPath`, and `node:22-bookworm-slim` does not include `git` → `npm install` aborts with exit 127. Each flag fixes a separate failure; quietly removing either re-introduces a different build-time crash.
- **`backend/tests/integration/test_has_attachments_invariant.py::test_seeded_state_satisfies_invariant` is a seed-only test against the real DB.** The query inspects every row in `email_metadata`, not only migration-0010 rows, so any E2E artefact left behind by `test_forward_flow_outlook.py::bootstrap_attachment_message` (which intentionally sets `has_attachments=TRUE` via direct SQL to work around Outlook's empty SENT-folder attachment listing — see `e2e_guide.md`) flips this test red. The failure is data-dependent, not container-dependent.
- **The `default` network pins a fixed subnet (`10.89.42.0/24`, gateway `10.89.42.1`) for exactly one reason: the backend's `DEV_LOGIN_TRUSTED_HOSTS` needs a stable IP to list.** Browser requests reach uvicorn through Podman's port-forward, so `request.client.host` is the network **gateway** (`10.89.42.1`), never `127.0.0.1`/`localhost`. Without the pinned subnet Podman reassigns the gateway on each `compose down`/`up`, and `POST /auth/dev-login` (plus the DEV auto-login that rides on it) starts returning 403 `dev_login_not_localhost`. The subnet in `compose.yml` and the gateway in `backend/.env.docker`'s `DEV_LOGIN_TRUSTED_HOSTS` must change in lockstep.
- **`VITE_DEV_AUTO_LOGIN=true` lives in `frontend/.env.development` (a deliberate `!.env.development` exception in `frontend/.gitignore`), NOT in the frontend service's `environment:` block.** Vite loads `.env.development` only in `mode=development` (the dev server), so the flag reaches the browser bundle but NOT Vitest, which runs in `mode=test`. Moving it into compose `environment:` puts it in the container's `process.env`, which Vitest inherits and re-exposes on `import.meta.env` — that silently flips `LoginPage.test.tsx` into auto-login and breaks its manual-Dev-login-button assertions. The auto-login is gated in `AuthProvider` by `import.meta.env.DEV && import.meta.env.VITE_DEV_AUTO_LOGIN === 'true'`, so a production build never triggers it even if the flag leaks in.

### Production packaging — `compose.prod.yml` is standalone, NOT an overlay

The dev stack above is unchanged. Production runs a **separate, self-contained** `compose.prod.yml` *without* the dev file: `docker compose --env-file .env.production -f compose.prod.yml up -d --build`. Turning it into an overlay of `compose.yml` (the obvious "DRY it up" refactor) breaks two things silently:
- **`compose.override.yml` is reserved** by `/creacion-worktree` (per-worktree dev override, gitignored) — a versioned dev override under that name cannot coexist.
- **Compose *concatenates* `ports` across `-f` files**, so an overlay cannot REMOVE the dev-only published Postgres/backend ports; prod would keep exposing Postgres. The standalone file omits them outright (#2).

Other non-obvious prod rules:
- Both Dockerfiles are **multi-stage** (`dev` / `prod` targets); the image *name* is unchanged, so worktree stacks pinning `mailmanager-backend:latest` keep working. `dev` has no source `COPY` (the bind supplies the code + the override's `--reload`); `prod` bakes the code in and runs the image CMD (`python main.py` → uvicorn, **single process, no reload** — #7/#9). `backend/.dockerignore` excludes `tests/` + `Scripts/` from the prod `COPY` only (dev still sees them through the bind).
- **`VITE_API_BASE_URL` / `VITE_GOOGLE_CLIENT_ID` are build-time** (baked into the bundle by `vite build`, passed as build args). Changing the prod domain means **rebuilding** the frontend image, not just restarting it.
- **Caddy strips `/api` via `handle_path`**, so the backend keeps its routes at the root and never sees the prefix. The prod OAuth redirect URIs registered at Google/Azure must still include it (`https://DOMAIN/api/auth/{google,outlook}/callback`).
- **`.env.production` serves two roles**: compose interpolation (`--env-file`: `DOMAIN`, `ACME_EMAIL`, `SECRETS_DIR`, `POSTGRES_PASSWORD`, `VITE_*`) AND the backend service's `env_file` (runtime config). `POSTGRES_PASSWORD` therefore appears both standalone (interpolation) and inside `DATABASE_URL` — they must match. Template: `.env.production.example`; the real file is gitignored.
- **`SECRETS_DIR`** points the credentials mount at a directory holding ONLY the 2 JSON files (#10), read-only — never the dev folder that also carries the SQL dump.

## Claude Code Configuration

This project has a single contributor working from a single machine, so the split between `.claude/settings.json` (tracked) and `.claude/settings.local.json` (gitignored) — designed to keep developer- or machine-specific overrides out of the shared config — adds no value here. `settings.local.json` is intentionally not used: all Claude Code permissions, hooks, MCP toggles, and plugin configuration live in the tracked `.claude/settings.json`. The `.gitignore` entry for `settings.local.json` is kept as a safety net in case Claude Code recreates the file automatically when granting new permissions mid-session — if that happens, fold the new entries back into `settings.json` and delete the local file again.
